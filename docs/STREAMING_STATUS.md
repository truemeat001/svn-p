# 大工作副本的流式状态读取

默认 `SvnClient.status()` 不再先把整个命令输出读入内存并建立完整 XML 树。现在使用有界管道队列读取 `svn status --xml`，解析完一个条目就释放对应 XML 节点；仍然返回完整、保持顺序的 `StatusEntry` 列表。

这项改动主要降低状态解析和命令输出的额外内存，**不是虚拟化整个 GUI，也不意味着 SVN 扫描磁盘、提交或联网速度变快**。结果列表本身仍随文件数增长。当前文件列表、待提交控件、历史与差异有各自的限制，不应把本项内存数据扩展为整体桌面客户端的性能承诺。

## 正确性与失败边界

- 只改变只读状态命令；提交、更新、还原等命令执行路径不变。
- 保留中文和特殊字符路径、条目顺序、原生变更列表、正常但已归组的文件、属性、复制/移动、冲突、切换、锁定、外部文件标记和最后修改作者/修订。
- 只有收到格式完整的 XML、通过本实现的结构检查、读取结束、确认 SVN 退出码为零且 stderr 没有任何诊断输出后才返回列表。即使退出码为零，W155007 等告警也会使本次读取失败。超时、取消、XML 损坏、进程失败、诊断告警或超限均抛出错误，不把部分结果当作“干净工作副本”。
- 保留不使用 shell、关闭标准输入、`--non-interactive`、`--no-auth-cache`、`--ignore-externals` 和路径/peg 转义。没有加入认证提示、凭据写入或自动重试。
- 状态调用继续使用同工作副本的锁。等待锁也会检查取消和超时，并保持同线程重入行为。运行中的只读状态进程在取消、超时或异常后被终止并回收。
- 可通过 `status(cancel_event=threading.Event())` 从调用端取消。**本项未新增 GUI 取消按钮**；已有调用不传此参数仍兼容。

### 明确的资源限制

- stdout 每次最多读取 64 KiB，最多排队 4 块。另有正在读取/解析的块、XML 解析器和完整结果列表，不能把 256 KiB 当作整个调用的内存上限。
- stderr 持续排空，但只保留前 64 KiB；错误中会明确标记诊断截断。密码式 URL 信息在展示前清除，包括截断刚好落在密码内的情况。状态错误不再附带完整原始 XML stdout。
- 单次 XML 最大 512 MiB；两次完成条目之间最多接收 4 MiB，嵌套最多 64 层。超过即明确失败，不截断返回。巨大工作副本可使用 `status(paths=[...])` 查询更小范围。
- 拒绝 DTD/实体声明、NUL/UTF-16 输入及嵌套 entry 等异常结构。正常 SVN XML 为 UTF-8。这不是完整的 SVN XML schema 验证：为保持旧契约，没有 `wc-status` 的 entry 仍跳过，缺失属性仍使用原有默认值。
- 为兼容测试和自定义传输，覆盖 `client.command()` 的调用者仍可返回完整文本，但先执行同样的退出码/诊断检查，再由相同的增量解析器处理。**这种自定义传输自身的缓冲不在有界保证内**，普通系统 SVN 路径不使用它。

## 验证与复现

`tests/test_status_stream.py` 包含真实 Python 子进程管道测试：同时大量输出 stdout/stderr 后拒绝告警结果、零退出码 W155007、无告警的正常空状态、退出失败、诊断脱敏、超限、无效/截断 XML、超时回收、中断回收、提前取消、运行中取消、等待工作副本锁时取消/超时，以及兼容自定义命令传输。它们不是 SVN 替代实现，不能证明实际 SVN 版本、Windows 管道或仓库集成已经验收。

开发环境没有 `svn` / `svnadmin`，因此真实仓库测试仍跳过。还需要在原生 Windows 上验证安装的 SVN、真实大工作副本以及 GUI 连续操作。

合成解析对比：

```console
python -m unittest discover -s tests -p "test_status_stream.py" -v
python -m unittest discover -s benchmarks -p "test_*.py" -v
python benchmarks/benchmark_status_stream.py --sizes 1000 10000 100000 --repeats 3 --output benchmarks/status-comparison-new.json
```

Windows 将 `python` 换成 `py -3 -X utf8`。输出路径必须不存在；程序不覆盖已有数据，只使用自己的临时目录，不执行 SVN、不访问真实工作副本、服务器或网络。

脚本将冻结的旧版完整 XML 树算法与当前实际 `status()` 的兼容传输路径进行同次对比，并逐条核对完整字段和顺序。输入 XML 在计时和内存追踪前生成；每项一次预热、三次独立计时，再单独一次 `tracemalloc`。内存只是 Python 可追踪分配，不含输入、RSS、原生库、操作系统管道或子进程；时间也不含真实 SVN、进程启动或 GUI。

原始结果见 [results-status-stream-linux-20261103.json](../benchmarks/results-status-stream-linux-20261103.json)。其中记录环境、每次样本、源码哈希和源码是否在执行中变化。旧的全套合成基准说明见 [PERFORMANCE.md](PERFORMANCE.md)，其历史数值不能当作新版本结果。

## 本次 Linux 合成结果

| 条目数 | 旧版完整树解析 | 当前增量解析 | 旧版峰值追踪分配 | 当前峰值追踪分配 |
| --- | ---: | ---: | ---: | ---: |
| 1,000 | 9.8 ms | 12.1 ms | 1.7 MiB | 1.3 MiB |
| 10,000 | 115.5 ms | 130.8 ms | 17.6 MiB | 6.4 MiB |
| 100,000 | 1,427.3 ms | 1,318.2 ms | 167.7 MiB | 47.6 MiB |

100,000 条目的峰值追踪分配降低约 **71.6%**。这次较小样本的时间反而更长，大样本略快，因此结论是显著减少额外内存，而不是对所有规模保证提速。全部条目内容和顺序一致；记录的 `source_changed_during_run=false`。这项测试没有测量系统 SVN 进程管道的耗时或内存，其安全性另外由子进程回归测试覆盖。
